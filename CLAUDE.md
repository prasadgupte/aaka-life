# Aaka — Claude Code Context

Local-first family calendar assistant on macOS, delivered over WhatsApp and Telegram.

**Design principle:** zero-token for common queries, privacy-sensitive (no personal data in git).
**Gateway:** OpenClaw (default) or ZeroClaw (fallback via `GATEWAY_BACKEND=zeroclaw`).

All runtime data (config, calendar, logs) lives in `$AAKA_CONFIG_DIR/` — outside the repo. `AAKA_CONTEXT` is semantic only (calendar labels etc.) and does **not** affect path resolution.

## Gateway Abstraction

All outbound messages and LLM calls go through `gateway/adapter.py`.
Switch backends with one env var — no code changes:

```bash
export GATEWAY_BACKEND=openclaw   # default
export GATEWAY_BACKEND=zeroclaw   # fallback
```

`gateway/adapter.py` dispatches `send_message()` and `call_llm()` based on this var.

## MCP Server — Claude as the Interface

`mcp/server.py` exposes Aaka's skills as native MCP tools. Claude Code loads it
automatically via `.mcp.json` when you run `claude` in this directory.

**This is a third access path — it does not replace the sensor or gateway:**

| Path | How | When |
|------|-----|------|
| Telegram / WhatsApp | Sensor → queue → executor | On the go, always-on (with VPS) |
| Registered agents (travel, tax) | HTTP gateway `:18790` | Agent processes in other dirs |
| Claude Code (interactive) | MCP tools → Python skills | Seated at the Mac, direct conversation |

**Available MCP tools:**

| Tool | Description |
|------|-------------|
| `today_schedule()` | Read today.md from synced calendar |
| `weekly_schedule()` | Read weekly.md |
| `add_event(title, date, ...)` | Write to Google Calendar |
| `list_tasks(filter)` | List open tasks (week/today/overdue/all) |
| `add_task(title, due_date, ...)` | Add a local task |
| `complete_task(num)` | Mark a task done by display number |
| `list_emails(label, member_id)` | Read Gmail by label |
| `save_email_attachment(msg_id, folder)` | Save attachment to a path |
| `add_note(topic, body)` | Append to a note log |
| `shopping_list(name, action, items)` | View/update a shopping list |
| `setup_status()` | Tier-aware setup check (JSON) |
| `bot_info()` | Name, members, timezone |
| `list_members()` | Members + bound WhatsApp/Telegram handles (id, name, role, source) |
| `add_member(name)` | Create a member (no aaka.yaml edit → `data/members_dynamic.json`) |
| `set_contact(member, handle, channel)` | Bind a handle (@lid/+E.164/telegram id) → member (dynamic allowlist) |
| `invite(name)` | Mint a one-time code + wa.me link to onboard someone (creates member if new) |
| `remove_member(member_id)` | Remove a dynamic member + unbind handles (yaml members protected) |
| `list_tools()` | Registered aaka Tools + schedule/placement/last-run (see `docs/aaka-tools.md`) |
| `register_tool(name, run, ...)` | Register/update a Tool (script, cron, placement, secrets) → `config/tools.yaml` |
| `run_tool(name, args)` | Run a Tool now and report back; returns its structured result |
| `set_tool_enabled(name, enabled)` | Enable/disable a Tool |
| `tool_logs(name, n)` | Recent run records for a Tool |

**Why Python-native, not HTTP:** MCP runs in the repo process on the same Mac that holds OAuth tokens — direct imports are faster and avoid the gateway overhead. The HTTP gateway exists for *other agent processes* that can't import aaka's Python.

**Adding a new MCP tool:** Add a `@mcp.tool()` function to `mcp/server.py`. Restart Claude Code (`/restart` or re-open the session) to pick it up. Keep tool docstrings accurate — Claude uses them for routing.

## Agent Pub/Sub Gateway

> **Full reference:** [`docs/AGENT-API.md`](docs/AGENT-API.md) — registration, endpoints, SDK, direct imports, auth.

Third-party agents (travel, research, etc.) integrate via `gateway/agent_api.py` on port 18790 (Mac, localhost only).

| Component | File | Purpose |
|-----------|------|---------|
| HTTP API | `gateway/agent_api.py` | `POST /v1/messages`, `GET/DELETE /v1/replies/{id}` |
| Python SDK | `gateway/agent_client.py` | `AakaClient(api_key).send()` / `.ask()` / `.add_event()` / `.add_task()` |
| Admin CLI | `admin/register_agent.py` | Register agents, list, revoke |
| launchd | `executor/com.aaka.agentapi.plist` | Auto-start on Mac login |

**Auth:** `X-Agent-Key` header. Key hash stored in `agent_registry.key_hash` (SHA-256). Key printed once on registration — not stored.

**Reply routing:** When a user message arrives at the sensor while an `agent_reply_requests` row is `waiting` for their `sender_id`, `router_sensor.py` intercepts it (after aaka's own `pending_confirms` check), writes it to `agent_replies`, and replies "✅ Reply received." to the user.

**DB sync:** The `com.aaka.dbsync` launchd (rsync every 15s) propagates agent tables between Mac and VPS automatically — no extra configuration needed.

**Quick start for a new agent:**
```bash
# Register
python3 admin/register_agent.py my-agent "My Agent Name"
# → save the printed AAKA_AGENT_KEY

# In agent code
from gateway.agent_client import AakaClient
client = AakaClient(api_key=os.environ["AAKA_AGENT_KEY"])
seat = client.ask("Window or aisle?", options=["Window", "Aisle"])
```

**New DB tables:** `agent_registry`, `agent_reply_requests`, `agent_replies`, `scheduled_messages` — all in `butler.db`.

**Scheduled outbound** — queue email, Telegram, or WhatsApp for future delivery via the always-on VPS sensor (`sensor/scheduled_sender.py` cron, every 60s). Synced Mac→VPS via `executor/vps_sync.py`; results (status, message_id) synced VPS→Mac.

```python
# Schedule email at a specific time (ISO8601 + TZ required)
client.send_email("alex", "Flight confirmed", "Departs 14:30",
                  schedule_at="2026-06-01T09:00:00+02:00")
# → {"id": "...", "status": "pending", "scheduled_at_utc": "...", "to": "..."}

# Generic (telegram, whatsapp, email)
client.schedule_outbound("telegram",
    {"channel_id": "12345678", "text": "Reminder: meeting in 15 min"},
    schedule_at="2026-06-01T09:45:00+02:00")

# Poll status
msg = client.get_scheduled_message(id)   # status: pending → sent/error
msgs = client.list_scheduled_messages(status="pending")
client.cancel_scheduled_message(id)      # only if still pending
```

Channels: `email` · `telegram` · `whatsapp`.
Email payload: `{to_member_id, subject, body, html_body?, from_member_id?}` — only registered family members with a configured email accepted.
Telegram/WhatsApp payload: `{channel_id (or recipient), text, silent?, reply_markup?}`.
`schedule_at` MUST carry an explicit timezone offset; naive datetimes are rejected (422). Omit for near-immediate delivery (~60s via VPS cron).

## Architecture: Away / Home Split

| Component | Where | Purpose |
|-----------|-------|---------|
| `sensor/router_sensor.py` | VPS (Docker) — **Away** | Receive message, triage intent, queue |
| `executor/queue_worker.py` | Mac (native) — **Home** | Poll queue, execute side-effects |
| `skills/` | Both paths | Calendar, tasks, mail |
| `aaka_queue/` | Both paths | Shared SQLite queue API |

**Away** (sensor) is side-effect-free — no Google API calls, no calendar writes.
**Home** (executor) runs on Mac where OAuth tokens live.

## Gotchas

- `sensor/router_sensor.py` is Away (VPS-only) — no Google API calls
- `executor/queue_worker.py` is Home (Mac-only) — needs OAuth tokens
- `GATEWAY_BACKEND=zeroclaw` switches to ZeroClaw if needed (fallback)
- WhatsApp QR re-scan required if moving to a new machine (Telegram bot token is portable)
- `QUEUE_DB` env var overrides queue DB path
- `AAKA_CONTEXT` is now **semantic only** — paths no longer include a `family/` subdirectory
- Tokens live in `$AAKA_CONFIG_DIR/tokens/` (not `config/`) — `auth_for()` uses `TOKENS_DIR`

## Standing Rules for Claude

**When fixing a new bug or discovering a new failure mode:**
1. Append a check to `admin/diagnose.sh`
2. Append a test to `admin/test.sh`

This keeps the admin scripts as a living runbook — not a snapshot.

---

**When adding or changing a user-facing feature (intent, command, shortcut, behaviour):**

Update ALL of the following — no exceptions:

1. **`CLAUDE.md` Intents table** — add/update the row with intent name, trigger, shortcut, handler summary
2. **`docs/manual.md`** — add or update the relevant section with usage examples
3. **`sensor/router_sensor.py` menu string** — the `intent == "menu"` reply block users actually see
4. **`cli.md`** — add a dry-run example if the intent is invokable from the CLI
5. **`admin/test.sh`** — append a smoke test covering the new/changed path

For intents that are zero-token (local sensor reads): mark them as `(0 tokens)` in docs.
For intents that call LLM: note the approximate token cost.
For intents that are sensor-direct (VPS executes immediately, no queue): note `(VPS direct)`.

The `/menu` command is the single most-read piece of documentation — keep it tight but complete.
If the menu is getting long, group commands; don't silently drop entries.

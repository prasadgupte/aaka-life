# WhatsApp → Telegram parity: always-on WhatsApp on the VPS

**Status:** spec / proposal (not built). **Goal:** WhatsApp responds 24/7 like
Telegram — i.e. even when the Mac executor is asleep — by moving the Baileys
`wa-sidecar` from the Mac into the always-on VPS sensor. Baileys `6.17.16`, no
OpenClaw.

## Why this is now viable

- The session-pairing pain we hit was the Baileys **7.0.0-rc handshake bug**, not
  an IP ban — home and work IPs failed identically; `6.17.16` fixed both. So the
  "datacenter IP" worry is largely moot here, and the 1blu VPS IP is not a
  WhatsApp-flagged cloud range (AWS/GCP are). **Gate it empirically:** run
  `node wa-sidecar/netcheck.js` on the VPS first — if the raw WS holds and a QR
  issues, we're clear to proceed.

## Current vs target

**Current (Mac-only):** everything is co-located on the Mac over localhost.
```
WA phone ──▶ wa-sidecar(:18792, Mac) ──▶ wa_inbound(:18793, Mac)
                    ▲                          │
                    │                    router_sensor.route()
     egress/whatsapp.py POST /send ◀──── 0-token reply
                    ▲
     Mac executor (queued-intent replies) ── localhost POST
```
Always-on only while the Mac is awake.

**Target (VPS always-on):** sidecar + receiver move to the VPS container; the Mac
executor reaches the VPS sidecar for the reply leg of *queued* intents.
```
WA phone ──▶ wa-sidecar(:18792, VPS) ──▶ wa_inbound(:18793, VPS)
                    ▲                          │
                    │                    router_sensor.route()  ← 0-token replies
     local POST /send ◀──────────────────────┘   sent VPS-side (24/7) ✅
                    ▲
     Mac executor (queued-intent reply) ──▶ outbound queue ──sync──▶ VPS delivers
```

## The one hard design decision: the Mac→VPS outbound leg

0-token replies (`status`, `/menu`, `/today`) are generated by the router **on the
VPS** and sent via the **local** sidecar — trivially always-on. The only tricky
part is replies to **queued** intents (e.g. `add event`), which the **Mac
executor** produces after doing the calendar write. Those must reach the VPS
sidecar. Two options:

- **A — Route through the existing outbound queue (recommended).** aaka already has
  a Mac→VPS outbound path: `scheduled_messages` + `executor/vps_sync.py` →
  `sensor/scheduled_sender.py` (VPS cron) delivers. Make the executor's WhatsApp
  sends enqueue there instead of a direct POST; the VPS-side sender POSTs to its
  **local** sidecar. Reuses proven infra, matches the split-arch principle
  ("executor never touches a channel directly; it queues, the VPS delivers"),
  survives network hiccups. Cost: a small routing branch in `whatsapp.py`/egress
  keyed on "is the sidecar remote?".
- **B — Direct authed HTTP Mac→VPS.** Expose the VPS sidecar `/send` via Caddy with
  an auth token (or an SSH tunnel). Simpler conceptually, but adds a new
  authenticated ingress surface and a failure mode when the link is down. Not
  recommended.

**Decision:** A. A new config flag `WA_SIDECAR_LOCATION=mac|vps` (or deriving it
from `WA_SIDECAR_URL` being localhost vs remote) selects: local direct POST (Mac
install) vs enqueue-to-outbound (executor when the sidecar lives on the VPS).

## Component changes

1. **Image** — re-add Node to `sensor/Dockerfile` behind a build arg (e.g.
   `WITH_WHATSAPP=true`), install **only** `wa-sidecar/`'s deps (baileys 6.17.16 +
   qrcode) — **no OpenClaw**. Keep the default image Telegram-only/lean.
2. **entrypoint.sh** — when `whatsapp ∈ ENABLED_CHANNELS`: start `wa-sidecar`
   (`node /app/wa-sidecar/index.js`) and `wa_inbound` (uvicorn) alongside the
   telegram supervisor (background + restart loop, like the Telegram one). Auth
   dir → `/config/whatsapp-auth` (host volume).
3. **`gateway/channels/whatsapp.py`** — honor `WA_SIDECAR_URL` (default
   `http://127.0.0.1:18792`); on the Mac executor, when the sidecar is remote,
   enqueue via the outbound path instead of POSTing (per Decision A).
4. **compose.prod** — `ENABLED_CHANNELS=telegram,whatsapp`; mount
   `/opt/aaka-config/whatsapp-auth`; bump `mem_limit` (Node ~+150 MB).
5. **backup** — include `whatsapp-auth/` in the VPS→Mac backup (it's the session;
   losing it = re-pair).
6. **`admin/aaka.sh wa-pair`** — new helper: `ssh -L 18792:localhost:18792 <vps-host>`
   then open `http://localhost:18792/` to scan the QR against the VPS session.

## Pairing on a headless VPS

The sidecar's live-QR page binds `127.0.0.1` on the VPS. Pair by SSH-tunnelling the
port to your laptop and opening the page (or use the pairing-code `/pair` endpoint
over the tunnel). One-time; the session persists in the mounted `whatsapp-auth/`.

## Migration steps (ordered, reversible)

1. `netcheck.js` on the VPS → confirm the IP can pair. **Abort if not.**
2. Build the image with `WITH_WHATSAPP=true`; deploy with `whatsapp` disabled first
   (sidecar present but idle) to confirm Telegram is unaffected.
3. Enable `whatsapp`, pair via the tunnel, verify inbound `status` round-trips
   VPS-side (0-token path).
4. Wire Decision A; verify a queued intent (`add event …`) reply arrives over
   WhatsApp with the Mac executor doing the write.
5. Decommission the Mac sidecar services (`launchctl unload com.aaka.wasidecar*`).
   **Rollback:** re-enable the Mac services + set `WA_SIDECAR_URL` back to
   localhost; the Mac session is independent, so no data loss.

## Risk / open questions

- **Session portability:** the Mac's paired session can't be copied to the VPS
  (device-bound) — the VPS pairs fresh (a new linked device). Fine; WhatsApp allows
  ~4 linked devices.
- **One session only:** don't run the Mac *and* VPS sidecars against the same
  number simultaneously — pick one home for the session (VPS) to avoid 440
  conflicts.
- **VPS IP reputation:** re-run `netcheck` periodically; if WhatsApp ever starts
  refusing, fall back to a residential always-on box (Pi/old phone) or a
  residential proxy.

## Related / follow-on (smaller parity gaps)

- **Auto-registration** (both channels): trust-on-first-use with admin confirm — an
  unknown sender triggers an in-band "add them? `add <name>`" prompt to the admin,
  which writes `whatsapp:`/`telegram_id:` into `aaka.yaml`. Removes hand-editing.
- **Reactions:** wire `gateway/channels/whatsapp.py::send_reaction` (currently a
  no-op) to the sidecar for the ack UX Telegram has.
- **Read receipts:** call `sock.readMessages` in the sidecar on inbound so messages
  show as read (visible "it's working" signal).
- **Groups:** route WhatsApp group JIDs (currently DM-focused).
